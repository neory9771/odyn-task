# Which prompt is used where?

This folder defines the instructions and input builders for the two survey tasks. Training and inference use the same task format; dataset generation writes that format into each sample. It does not contain every LLM prompt in the project.

| Task | Definition | What it provides | Used by |
|---|---|---|---|
| **SFT1: claim → analysis program** | `authoring.py`: `AUTHORING_API_INSTRUCTIONS` | Survey API instructions, complete example, permitted calls and output requirements | Included in the SFT1 input by `analysis_input()` |
| SFT1 task and input | `survey.py`: `ANALYSIS_INSTRUCTION`, `analysis_input()` | Short task instruction; JSON containing API instructions, survey specification and claim | Dataset export and synthetic generation; prepared SFT1 samples are consumed by training and inference |
| **SFT2: evidence → research perspective** | `survey.py`: `SYNTHESIS_INSTRUCTION`, `INTERPRETATION_SPEC`, `synthesis_input()` | Interpretation instructions; JSON containing the study, original claim, executed program and API evidence | Dataset export and synthetic generation; E2E inference rebuilds the input from SFT1's actual evidence |
| Shared study context | `survey.py`: `survey_specification()` | Study notes and catalogue of variables, values and block identifiers | Both task inputs; catalogue encoding comes from `survey_metadata` |

## How a sample becomes the model prompt

Each prepared JSONL sample stores `instruction`, `input` and `output`:

```text
system message: config.system_prompt, when configured
user message:   sample.instruction + two newlines + sample.input
assistant:      sample.output during training; generated by the model at inference
```

The tokenizer applies the selected model's chat template. Qwen's thinking setting is supplied separately by configuration. The task's API/interpretation specification is inside the user input, not the system message.

For an existing dataset, **the prompt embedded in its JSONL is what the model sees**. Editing these Python constants does not rewrite an existing package. Inspect the sample's `instruction` and `input`, its manifest and the run's provenance when identifying the prompt used in a particular experiment.

Version markers: `authoring.py::CURRENT_CONTRACT_VERSION` identifies the authoring contract; `survey.py::PROMPT_VERSION` identifies the paired task builders. These identify different layers. Files under `configs/` supply model-specific system prompts and decoding settings.

## Other LLM prompts live with their workflow

Paths below are relative to `src/odyn_sft/`:

| Purpose | Location | Role |
|---|---|---|
| Judge research answers | `survey_evaluation/synthesis_judge.py::INSTRUCTION` | Evaluates answers against evidence facts and expectations; it is not sent to the answer model |
| Optional semantic review of analysis code | `survey_evaluation/analysis_judge.py::INSTRUCTION` | Reviews the analysis meaning against a frozen reference; execution and numerical contracts remain separate checks |
| Generate richer SFT2 target answers | `dataset_generation/synthesis_targets/writer.py::INSTRUCTION` | Optional LLM target-writing step during dataset generation; not the deployed SFT2 prompt |
| Rephrase input claims | `dataset_generation/claim_variants/paraphrase.py::WRITER_INSTRUCTION` | Optional input-variation generation |
| Check rephrasing preserves meaning | `dataset_generation/claim_variants/paraphrase.py::VERIFIER_INSTRUCTION` | Optional input-variation verification |

Reference contracts, expected directions and private gold are evaluation/generation artifacts. They must not be appended to the SFT1 or SFT2 inference prompt.
